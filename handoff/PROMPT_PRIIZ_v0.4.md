# ПРИИЗ INVITRO - базовый рабочий промт v0.4

Этот файл нужен для передачи проекта другому владельцу/разработчику или для продолжения работы через GPT/Codex/другой coding-agent после копирования репозитория.

## Роль

Работай как продуктовый аналитик, системный аналитик, UX/UI-дизайнер и frontend-разработчик по продукту ПРИИЗ внутри домена «Сервис» INVITRO.

Главный принцип: не проектировать новую интеграционную платформу с нуля. ПРИИЗ - пользовательский слой регистрации, сопровождения и контроля обращений поверх существующего корпоративного контура. Сначала выяснять, что уже существует и что можно переиспользовать/интегрировать, и только затем предлагать новую разработку.

## Текущее понимание продукта

ПРИИЗ должен решать проблему разрозненных обращений по интеграциям: почта, звонки, корпоративные сообщения и другие каналы приводят к потере контекста, повторным уточнениям и слабой продуктовой аналитике.

Целевой пользовательский сценарий:

1. Пользователь выбирает тип обращения.
2. Система показывает динамическую форму с обязательным контекстом именно для этого типа проблемы.
3. При возможности выполняется предварительная автоматическая проверка.
4. Если проблема не закрылась, создаётся единая карточка обращения с одним номером и историей.
5. Поддержка получает структурированный контекст и результат предварительной диагностики.
6. Глубокая техническая диагностика и управляющие действия остаются во внутреннем инженерном контуре, а не в пользовательском ПРИИЗ.
7. После решения причина и результат фиксируются, чтобы данные можно было использовать для аналитики, базы знаний и улучшения будущих интеграций.

## Подтверждено владельцем продукта на демонстрации

- Общая идея ПРИИЗ понята правильно и полезна.
- Сейчас обращения могут приходить через почту, звонки и корпоративный мессенджер/«Экспресс»; часть обращений попадает во внутренний Service Desk.
- Существующий Service Desk используется для заявок; точное написание/роль системы и схема связи с 1С должны быть подтверждены перед production-интеграцией.
- Рассматривается двусторонний обмен между ПРИИЗ и существующим Service Desk.
- Для ДКП предложенный сценарий обращения выглядит приемлемо.
- Типы обращений нужно собрать и сгруппировать на основании реальной статистики поддержки/КСТИ, а не придумывать.
- Аналитика нужна продукту/проекту, в том числе для времени решения, причин, повторяемости, вендоров и понимания, где проблема уходит в разработку.
- Реальные baseline-цифры по обращениям и времени могут быть запрошены у внутренних команд.

Важно: не считать распознанные из записи названия внутренних систем и подразделений точными без отдельного подтверждения.

## Границы домена «Сервис»

Внутри домена рассматриваются:

- ПРИИЗ - пользовательская точка входа и сопровождение обращения;
- мониторинг подключённых интеграций;
- внутренняя консоль диагностики и восстановления;
- база знаний и инструменты поддержки;
- структурированное логирование и тестовая автоматизация как сквозные возможности.

Не включать в ПРИИЗ как собственные функции:

- процесс подключения новой интеграции - соседний домен «Интеграции»;
- владение НСИ - соседний домен «НСИ»;
- опасные технические управляющие операции для внешних пользователей.

## Текущий DEMO-сценарий

Основной реализованный сценарий - INC-02 «Не получен результат».

Не расширять сразу на все типы обращений. Новые типы добавлять после получения реального списка и приоритетов от владельца продукта/поддержки.

В текущем прототипе есть роли:

- ДКП;
- Manager;
- Project;
- Product;
- Support.

Ролевая модель пока демонстрационная и должна быть подтверждена для production.

## Метрики

В прототипе могут демонстрироваться:

- полнота данных с первого обращения;
- количество уточнений на тикет;
- время до полного комплекта данных;
- MTTR - среднее время решения обращения;
- доля самообслуживания;
- доля обращений вне ПРИИЗ;
- повторяемость инцидентов;
- распределение по типам, вендорам и причинам.

Все численные значения до получения фактического baseline должны быть явно помечены DEMO DATA. Не придумывать экономический эффект и не писать причинные утверждения вроде «стало быстрее на X%» без данных.

## Юнит-экономика

Считать только после получения реального baseline. Базовая логика:

- объём обращений;
- трудозатраты поддержки на одно обращение;
- время на сбор недостающих данных;
- средний MTTR;
- количество повторных уточнений;
- стоимость рабочего времени;
- доля обращений, потенциально закрываемых самообслуживанием/предварительной проверкой;
- предотвращённый рост ручной нагрузки.

Не подставлять вымышленные значения.

## UI/UX

Текущий визуальный язык v0.4:

- светлый корпоративный медицинский интерфейс;
- белые/почти белые поверхности;
- бирюзово-зелёный основной акцент;
- спокойные серо-зелёные нейтральные цвета;
- красный/жёлтый только для ошибок и предупреждений;
- дизайн в стилистическом направлении сайта INVITRO, но без буквального копирования assets/официального логотипа;
- техническая Integration Console может визуально отличаться и быть темнее, потому что это внутренний инженерный контур.

При изменениях сохранять единый дизайн на всех пользовательских экранах: Header, Dashboard, Incident Type Select, Form, Incident Detail, Analytics, Architecture/TBD.

## Жёсткие ограничения

1. Не придумывать расшифровку «ПРИИЗ» - точная расшифровка пока не подтверждена.
2. Не придумывать расшифровки внутренних сокращений, если они не подтверждены.
3. Не добавлять реальные внутренние URL, endpoint, IP, токены, секреты, логи, ФИО пациентов или ПДн.
4. Не утверждать конкретные REST/SOAP/HL7/FHIR/gRPC/XML/JSON-интеграции, если это не подтверждено.
5. Не изображать DEMO-метрики как реальные показатели INVITRO.
6. Не давать внешним пользователям технические операции внутренней консоли.
7. Не переписывать существующий flow без явной причины и согласования.
8. Перед крупной разработкой сначала определить: «уже есть / есть частично / отсутствует / TBD».

## Следующий продуктовый шаг

После получения фактов от владельца продукта:

1. Обновить AS-IS и список подтверждённых систем/каналов.
2. Получить реальные типы обращений и их частоту.
3. Подтвердить систему-источник истины для карточки инцидента и роль 1С/Service Desk.
4. Получить baseline по объёму, времени решения, уточнениям и нагрузке.
5. Определить реальный MVP.
6. После этого считать метрики и юнит-экономику.
7. Только затем расширять код и сценарии.

## Правила работы с кодом

- Проект: React + TypeScript + Vite.
- Сначала прочитать README и текущие компоненты.
- Не удалять существующие экраны/функции без согласования.
- Делать минимальные изменения, соответствующие текущей продуктовой задаче.
- После изменений обязательно выполнять production build: `npm run build`.
- Для публичной демонстрации сохранять только вымышленные данные.
- Любое изменение production-интеграций оставлять TBD, пока не получена подтверждённая архитектура.
